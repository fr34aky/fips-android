# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Android port of the FIPS mesh daemon, embedded in a `VpnService` app. A Rust JNI shim (`shim/`) runs the fips node in-process; the Kotlin app (`android/`) provides the VPN tunnel, per-app split tunnel, and Material 3 UI. Selected apps reach the mesh over `fd00::/8` with `.fips` DNS while keeping normal internet through a userspace forwarder.

## Build & test commands

```bash
# Rust shim → android/app/src/main/jniLibs/<abi>/libfips_android.so
./build-native.sh                # all ABIs: arm64-v8a, armeabi-v7a, x86_64
./build-native.sh arm64-v8a      # single ABI for faster iteration

# Host-side Rust tests (engine lifecycle, DNS proxy, packet codecs — everything but the JNI surface)
source ./android-env.sh && (cd shim && cargo test)
# Single test: (cd shim && cargo test dns::tests::name_of_test)

# Two-node host smoke test of the embedding seam
source ./android-env.sh && (cd smoke && cargo run)

# APK (debug; toolchain paths are machine-specific — see android/local.properties)
cd android && JAVA_HOME=~/.local/jdk-17 ~/.local/gradle-8.7/bin/gradle assembleDebug
# → app/build/outputs/apk/debug/app-debug.apk; install with adb install

# Release: one signed APK per ABI + sha256 + unstripped .so → dist/v<versionName>/
./release-build.sh                # all ABIs; or pass a subset, e.g. arm64-v8a
```

`source ./android-env.sh` is required before any cargo command:
- Cross builds: sets the NDK r27c linker/CC/AR (API 24 floor — `getifaddrs` in fips's STUN code).
- **Host builds too**: it pins `LIBCLANG_PATH=/usr/lib/llvm-18/lib`, overriding a machine-wide ESP32/Xtensa libclang that breaks bindgen (`rustables`) with an `assertion failed 4 != 8` panic. The override is deliberately unconditional (an already-set `LIBCLANG_PATH` loses) — point elsewhere with `FIPS_LIBCLANG_PATH`, as CI does.
- Both machine paths have env overrides so the script needs no editing off this machine: `FIPS_NDK_HOME` (NDK location) and `FIPS_LIBCLANG_PATH`.

Toolchain: Rust 1.94.1 (pinned in `rust-toolchain.toml`), NDK r27c at `$HOME/android-ndk-r27c`, JDK 17 at `~/.local/jdk-17`, Gradle 8.7 at `~/.local/gradle-8.7`, Android SDK platform-34.

There is no Kotlin test suite; every Kotlin path is verified by a human looking at a screen — a wiped emulator (the `fips-firstrun` AVD) for first-run and settings-migration paths, a real device (Pixel 9 Pro) for anything involving Wi-Fi, Doze, or the hotspot, which the emulator cannot test. Say which was used when changing Kotlin. Rust tests live as `#[cfg(test)]` modules inside `shim/src/*.rs` (`config`, `dns`, `engine`, `filter`, `forward`, `meshhttp`, `meshtcp`, `packet`).

## CI (`.github/workflows/`)

`build.yml` runs on every push to `main` and every PR, and mechanically enforces four constraints this file states in prose — check it before assuming a rule is only advisory:
- **fips pin sync**: the `rev` in `shim/Cargo.toml` and `smoke/Cargo.toml` must match *and* appear in both `Cargo.lock`s (a bumped manifest with a stale lock quietly builds the old fips; the fix is `cargo update -p fips`).
- **ABI list sync** between `build-native.sh` and the debug `abiFilters` in `android/app/build.gradle.kts`.
- **Page alignment** per ABI, read out of the built `.so` with `llvm-readelf` (0x4000 on arm64/x86_64, 0x1000 on armeabi-v7a).
- **APK contents**: all three `lib/<abi>/libfips_android.so` present in the debug APK, which is uploaded as an artifact.

The `checks` job also runs the host suite as `cargo test --locked`, so a lockfile that drifts from the manifest fails there too. The `android` job is the only place all three ABIs are cross-compiled — it is the meaningful check on a fips pin bump.

There is no automated security scan in CI (the Anthropic security-reviewer workflow was removed in September 2026; reviews are done by hand). `SECURITY-REVIEW.md` is the context for that manual review: the trust boundaries, and the list of deliberate design choices that are *not* findings. CI holds no secrets at all — release signing happens on a workstation — so "Require approval for all external contributors" (Settings → Actions) guards runner minutes, not credentials, and only covers users without write access. The `security-review` GitHub environment and its `CLAUDE_API_KEY` secret outlived the workflow; they are unused and should be deleted from the repo settings, since any job that declares that environment regains the key after a self-approval. `main` requires the `checks` and `android` status checks to pass before a merge (branch protection, since 2026-09-15; not strict, so a PR need not be rebased onto the latest `main` first, and admins can bypass). Before that, several PRs were merged while `android` was still running.

`PR-REVIEW.md` is the maintainers' review checklist — the criteria applied to incoming PRs, several of which exist because the failure already happened once. Read it before reviewing or opening one.

## The fips dependency

`shim/` and `smoke/` depend on fips as a **pinned git dependency**: `fr34aky/fips` @ branch `android-hooks` (rev in both `Cargo.toml`s must stay in sync). That fork carries the embedder hooks the shim needs: `Node::enable_app_owned_tun()`, `Node::set_socket_protect()`, `Node::tun_packet_processor()`, public `ControlReadHandle::query`, `Node::control_command_handle()` (a `ControlCommandHandle` that routes the mutating `connect`/`disconnect` commands onto the rx_loop without a control socket), the `show_lan_peers` snapshot query (mDNS sightings registry fed by `poll_lan_rendezvous`), `LanRendezvousConfig.exclude_addrs` (keeps tunnel addresses out of mDNS adverts), `UdpConfig.share_port` (two UDP instances of one node on one port: puts SO_REUSEPORT/SO_REUSEADDR on *before* bind for that instance — fips otherwise sets them after bind on purpose, so a second bind of an occupied port fails loudly — and every instance sharing the port must set it), and `UdpConfig.dial_prefixes` (dial-scoped UDP instances: a scoped instance wins outbound selection for remotes inside its CIDR prefixes and is invisible to generic selection and the mDNS advertised-port pick — the FIPS Hotspot seam), family-aware hostname resolution in the UDP transport (`resolve_socket_addr_for`, @ 657886c: a static peer given as a hostname is dialed by transport *type*, so the transport resolves the name itself and used to take the resolver's first answer — on a DNS64/NAT64 carrier that is a synthesized AAAA, unusable from the `0.0.0.0` socket, and every handshake failed with EAFNOSUPPORT/os error 97; it now takes the first answer in its own family and refuses a numeric remote of the other family with a message naming both), `NostrRendezvousConfig.open_discovery_max_peers` (@ ae22165 + f4a811e: ceiling on the peers this node dials from adverts, in total — queued + connecting + connected; inbound links are not counted; 0 = no ceiling of its own. The reconciler remembers which peers came from the overlay and prunes that set to the live ones on EVERY sweep, knob or not — the first cut pruned only under the knob and grew forever on every existing `policy: open` server, caught by two independent reviews — and dials the freshest advert first, since the cache is up to an hour old and both device runs filled a cap of 3 with entries that no longer answered — the Settings "Discover peers via Nostr" seam), and `Node::nostr_rendezvous_arc()` + `NostrRendezvous::relay_status()` (a `Vec<RelayStatusView {url, status, connected}>` off nostr-sdk's relay pool — fips fixes that pool at node start and reports nothing about it, so this is how the Overview shows which relays are actually connected). mDNS is compiled in unconditionally and gated at runtime by `node.rendezvous.lan.enabled` (shim knob `enable_lan_mdns`, default off in the shim but default ON from the app since 0.3; the Kotlin side pairs it with a `MulticastLock` held only on Wi-Fi, or while a FIPS Hotspot is joined. Discovery over the phone's OWN tethering hotspot works without the lock — device-verified on 0.6.0, underlay cellular, a laptop running fips on the hotspot was discovered and linked — so do not extend the lock to tethering. That is also the only way a tethered device gets the mesh: tethered traffic is kernel-forwarded with no UID, netd's VPN rule matches `iif lo uidrange` only, and tethering never picks a VPN as upstream, so it cannot be captured by the `VpnService` or listed as a mesh app — the hotspot overlay forces LAN mDNS on).

The local `fips/` directory is a **git worktree of `~/fips` on `android-hooks`**, ignored by this repo — it is NOT what builds use. To develop against it, add to `shim/Cargo.toml` (and `smoke/Cargo.toml`):

```toml
[patch."https://github.com/fr34aky/fips"]
fips = { path = "../fips" }
```

When bumping the pin: change the `rev` in both `Cargo.toml`s and update both `Cargo.lock`s. `smoke/Cargo.lock` deliberately pins `rustables` 0.8.7 (known-good against the host libclang).

## Architecture

Everything crosses the JNI boundary as JSON strings — hand-written JNI (`jni_api.rs`, thirteen `Java_org_fips_android_FipsNative_*` exports: start/stop/status/isRunning, deriveIdentity, dnsServer, onNetworkChanged, networkHint, query, connectPeer, resolveNpub, recentLogs, meshHttpGet), no UniFFI. `FipsNative.kt` is the Kotlin `external fun` mirror. Panics are caught at the boundary.

Data path (the core seam): Kotlin's `VpnService` establishes the TUN (addresses = the node's fips /128 + an IPv4 source for clearnet, routes `fd00::/8` + `0.0.0.0/0`, plus `::/0` only while the underlying network has IPv6 internet — advertising it unconditionally black-holes IPv6 because the forwarder's userspace stack SYN-ACKs before dialing, defeating Happy Eyeballs; without `::/0`, two host routes keep AAAA queries — and thus AAAA-only `.fips` names — resolving: `2000::/128` satisfies netd's AI_ADDRCONFIG probe (UDP connect to `2000::`) and `2001:4860:4860::8888/128` satisfies Chromium/WebView's own IPv6-reachability probe (UDP connect to Google DNS, cached 60 s — without it `.fips` browsing dies exactly one minute after landing on a v4-only underlay); MTU 1280) and hands the fd to the shim, which dups it. When the IPv6 decision flips (network switch or link-properties change), the service re-establishes the tunnel and passes the NEW fd to `onNetworkChanged`; every rebind also passes a freshly regenerated config JSON so per-network state (the hotspot transport) rides the same path. A plain underlying-network switch that leaves the IPv6 decision alone does **not** restart the node (since the netmon pin, fips `android-hooks` @ bf6f442): the node's protected wildcard sockets route per packet over the new default network, and fips's `node.netmon.*` detector heartbeats the peers whose path moved (on by default; its netlink wake is refused to apps by SELinux, so the service pokes it through `FipsNative.networkHint()` → `Node::netmon_trigger()` the moment the callback fires, with the 5 s poll as backstop) so the far side re-pins within one RTT — sessions and routes survive. Only an IPv6-route flip, a FIPS Hotspot join/leave, and a changed mesh-app selection still rebind — the last because `addAllowedApplication` is fixed at `establish()`: the service records the set each tunnel was built with (`tunnelMeshApps`), `rebindOnce` replaces the tunnel whenever the stored selection differs, and the pickers nudge it through `FipsVpnService.requestRebind()` (`ACTION_CONFIG_CHANGED`) once per visit — from `onPause`, skipped on a rotation, and not per toggle, since every rebind is a ~2 s node restart. A nudge that arrives while the first connect is still establishing is deferred until the engine is up rather than raced against it. Network callbacks are coalesced, never dropped: a hand-over emits a burst of them over seconds while a rebind (full node restart) takes seconds itself, so requests queue on a flag served by a single worker that re-checks after every pass — the burst always ends with a rebind against final network state. Validated networks are preferred over unvalidated ones (a dying Wi-Fi keeps its transport for 10–30 s; follow the OS default to cellular instead). `pump.rs` runs reader/writer/bridge threads over the dup'd fd; each outbound packet goes through DNS intercept, then a mesh/clearnet classifier: `fd00::/8` goes through the node's own `TunPacketProcessor` (forward with MSS clamp / hairpin / ICMPv6 respond / drop — byte-identical to the daemon's system-TUN path), everything else to the userspace forwarder. The mesh→app direction passes the stateful inbound firewall (`filter.rs`, shim knobs `inbound_filter` default-on + `inbound_ports`): new inbound flows are default-denied unless the port is allowlisted, replies to outbound-initiated flows (4-tuple flow table fed by the reader) and ICMPv6 always pass, and non-TCP/UDP/ICMPv6 next-headers are dropped unparsed.

- `engine.rs` — singleton node lifecycle on a dedicated current-thread tokio runtime: in-memory `fips::Config` → `Node::new` → `enable_app_owned_tun` → `set_socket_protect` → `start`. Status/query served lock-free from `ControlReadHandle` snapshots; the `relays` array in `status_json` comes from a task on the node runtime (the relay pool can only be awaited there) that refreshes a shared slot once per `status_json` call (a `Notify` permit, so a backgrounded app costs no wakeups). `network_changed` restarts the node on the SAME tun fd (tunnel stays up; fips has no runtime socket-rebind API).
- `dns.rs` — mesh names: a `.fips` query whose label is in the app's hosts file (shim knob `hosts_path`; fips's own `name npub` format, read through fips's `HostMapReloader`, re-read on an mtime change with one stat per `.fips` query — so an edit needs **no rebind**) is re-asked as `<npub>.fips` and the reply re-issued under the asked name (`npub_query` / `answer_as_asked`). fips has this feature itself but only for the hardcoded `/etc/fips/hosts`, which an app cannot write; the responder still has to see the npub query because answering is what registers the identity with the node, so the shim must not answer from the map alone. Names are single labels (fips's `validate_hostname`): `www.home.fips` does not resolve. Otherwise: covered-app DNS is sent to the `fd00::53` sentinel (`engine::DNS_SENTINEL`, exposed as `FipsNative.dnsServer()`), NOT the node's own tun /128 — the kernel would deliver packets addressed to the interface's own address locally, so they'd never reach the TUN fd. The pump intercepts port 53 to that sentinel: `.fips` names → in-process responder at `[::1]:5354`; everything else → configured upstreams over protected sockets; SERVFAIL on total failure.
- `forward.rs` — userspace clearnet forwarder (`ipstack`-based tun2socks; TCP/UDP, not ICMP) dialing protected sockets per flow, so covered apps keep normal internet.
- Socket protection: the node announces every underlay socket fd to the shim's hook, which crosses JNI (JavaVM + GlobalRef, callable from any thread) to `VpnService.protect()`. Not covered (no fd access): nostr-sdk relay websockets, mDNS — benign because the fips app itself is not captured by the per-app tunnel.
- `config.rs` — `ShimConfig` JSON → validated `fips::Config` (knobs incl. `worker_threads`, `battery_saver`, and `fips_yaml` — a raw fips.yaml base config parsed by fips's serde); `derive_identity` produces the nsec/npub/fd-address triple. Identity is generated in Rust and persisted via Android Keystore (`SecureStore.kt`/`IdentityStore.kt`). `fips_yaml` (a raw fips.yaml that becomes the base config and supersedes the structured settings, with the hotspot overlay then ignored) is still supported by the shim but **no longer reachable from the app** — the Settings section was removed in the 0.3 UI overhaul and `ConfigStore.RETIRED_KEYS` deletes any stored value on first run, because a stale one would keep overriding everything with no UI left to clear it.
- `logbuf.rs` / `lib.rs::init_logging` — 1000-line ring buffer behind the `tracing` writer (fanned out to logcat), drained by `recentLogs` for the in-app log viewer. The subscriber installs once per process but the level filter sits behind a reload handle, so a log-level change takes effect on the next connect (every engine start re-calls `init_logging`) without killing the app process.
- `packet.rs` — IPv6/UDP build+parse for the DNS proxy (the UDP checksum is mandatory over IPv6).
- `names.rs` / `meshudp.rs` — public domain names over fips (`www.example.org` → a mesh node), the phone half of `fr34aky/fips-pub-domains` (spec and docs live there: `docs/spec.md`, `docs/android.md`; the crates `pubdom-core` (policy, no I/O) and `pubdom-resolve` (relays, legacy TXT verification, pin file) are pinned git deps in `shim/Cargo.toml` like fips; the repo is public). The DNS proxy asks `Names::lookup` for every non-`.fips` name before the upstreams: pins first; online the `_fips-dns.<domain>` TXT record from the configured upstreams (DNSSEC-validated when the zone is signed), a claim from the relays only after a TXT hit, then step 3 — a DNS query to the domain's server over the mesh, sent from the node's own address through a smoltcp **UDP** socket (`meshudp.rs`, the UDP twin of `meshhttp.rs`; `Divert` now keys UDP flows too), answered `CNAME <npub>.fips.`; when that names a node other than the server just answered, an ICMPv6 echo through the same stack must come back within 1.5 s (fips drops traffic for unknown nodes silently, so nothing else tells a real node from a bogus zone entry) — and the reply the app gets carries that node's `fd…` AAAA with the public addresses suppressed. `None` from it is "not over fips" and the query goes upstream unchanged: a name never becomes unreachable because of this code, and a claim alone never resolves — except offline, when its DNSSEC proof verifies against the root key (spec §5.5; needs a mesh relay, configured below). Shim knobs `names_pins_path` (set = on; the app-private `names-pins.json`, same schema as the desktop daemon's), `names_mesh_relays`, `names_allow_unverified_offline`; Settings → "Public domain names over fips" (`public_names`, `DEF_PUBLIC_NAMES` = true) decides whether the path is sent, and the "Mesh relays for public names" field below it (`names_mesh_relays`, `ws://<npub>.fips[:port]` per line, validated by `ConfigStore.normalizeMeshRelay`) lists relays on fips nodes. nostr-sdk's sockets cannot reach `fd00::/8` from this app, so `meshtcp.rs` gives each mesh relay a loopback listener and carries every accepted connection over the in-process smoltcp TCP stack (same device and `Divert` path as `meshhttp.rs`); the resolver is handed `ws://127.0.0.1:<port>/<token>`. Loopback is shared by every app and the connection leaves from this node's address, so the listener admits only the holder of that random path token (checked and stripped from the upgrade request before anything touches the mesh), at most 4 connections per relay. The pipe blocks on one event channel (mesh packets and local reads) with bounded buffers both ways (the local reader pauses at 256 KiB; local writes time out after 200 ms so the stack keeps running), and the listener blocks in `accept` until `Drop` wakes it — an idle relay connection costs a wakeup every 30 s plus smoltcp's keep-alive. With a mesh relay configured, an offline phone can verify a domain it never saw from the DNSSEC proof in its claim. Not yet on the phone: the TCP fallback for a truncated step 3 answer (a CNAME never is) and a network-state flag — an unreachable upstream simply takes the offline path (mesh relays, then pinned domains only); `network_hint` flushes the resolver's caches so the next lookup re-decides.
- `meshhttp.rs` — in-process HTTP GET to a mesh node (`FipsNative.meshHttpGet`, used by the Mesh names sync). The app's own UID is outside its tunnel whenever mesh apps are selected (and must stay out — see the no-selection note below), and a VPN network refuses `bindSocket` from a UID it does not cover, so a Kotlin socket cannot reach `fd00::/8`. Instead a smoltcp TCP client speaks from the node's own address: its packets go through the node's `TunPacketProcessor` + outbound channel exactly like an app's, and the pump's bridge hands replies (and ICMPv6 errors quoting them) back through `Divert` — keyed on (remote addr, remote port, local port), local ports 61000–65535 above the kernel's ephemeral range — before the inbound firewall and the TUN. It first asks the local `.fips` responder for `<npub>.fips`, since that is what registers the destination identity with the node (without it the node answers the SYN with destination-unreachable).

The shim crate is both `cdylib` (the .so Kotlin loads) and `lib` (so host tests can exercise everything except the JNI surface itself).

Kotlin side: `MainActivity` hosts bottom-nav fragments (Overview / Settings / Diagnostics), `FipsVpnService` owns the tunnel + foreground notification + network-change handling (ConnectivityManager callback → `setUnderlyingNetworks` + `onNetworkChanged`), `OverviewFragment` shows the identity, the "Nostr relays" card (`status.relays`, each public relay with its live connection state), and owns backup/restore (reveal the nsec + clipboard copy flagged `EXTRA_IS_SENSITIVE`; restore validates a pasted key through `deriveIdentity` and stores the bech32 form it echoes back — never pass that function an empty string, which means "generate" and would silently mint a new identity). Restore and regenerate are blocked while `FipsNative.isRunning()`. `HostsActivity` (Overview's "Mesh names" card) edits the name → npub address book; `HostsStore` owns it, and the file `files/hosts` IS the store — no prefs copy — written via temp + rename because the shim may read it at any moment, with `nameError` mirroring fips's `validate_hostname` (a name fips rejects would be listed in the app and never resolve) and npubs validated through `FipsNative.resolveNpub`. `buildConfigJson` always sends `hosts_path`, file or no file, so the first name added while connected works. Optionally the same screen pulls names from a node running fips-ui (`HostsSync`, off by default): `GET /api/hosts` on the upstream's fips0 address over `meshHttpGet`, hourly by default (fips-ui's own default is 5 min — too much wake-up for a phone) and on Sync now, only while connected; a connect resumes the schedule rather than pulling. The names go into fips-ui's marked block (`# >>> fips-ui sync from <npub>` … `# <<< fips-ui sync`) at the END of the hosts file, so a synced name wins over a local one; `HostsStore.load`/`save` see only the lines outside it, `loadSynced`/`saveSynced` only the block. Semantics follow fips-ui `server/hosts-sync.ts`: validated entries, ≤ 2000, an answer carrying `error` never taken as "no names", unreachable/403 backs off to daily, turning sync off removes the block. fips-ui's guard drops TCP from npubs not on its allow-list in the kernel, so a missing viewer entry shows as a timeout, not a 403. Diagnostics' probe field takes a mesh name too. `AppPickerActivity` selects the captured apps (with no selection — or when every selected app has been uninstalled — the tunnel allows only the fips app itself **and claims only `fd00::/8`: no default route, no DNS server**. Capturing ourselves with the full routes was never the no-op it was taken for: the app's own DNS lookups and relay sockets went into the tunnel, and during node start nothing serves it yet — the pump, its DNS proxy and the forwarder only come up once `start` returns — so the bootstrap peer's hostname sat in the resolver's ~10 s timeout, the first handshake failed, and a fresh install took up to ~25 s to its first link. Selecting an app rebuilds the tunnel with the full routes), `ConfigStore` holds the settings, renders them into the shim's config JSON, and owns their defaults as `DEF_*` constants — read those via `ConfigStore.lanMdns()`/`hotspotEnabled()`/`DEF_*` rather than repeating a literal at a `getBoolean` call site, or the service and the UI drift apart. The Diagnostics tab is `TroubleshootFragment.kt` (the class name does not match the tab label); `Updater.kt`/`UpdateUi.kt` implement the in-app updater. FIPS Hotspot (Settings toggle, API 29+, needs the fine-location runtime permission — Android hides SSIDs/scan results without it): while connected, the service auto-joins the open SSID `!FIPS` via two paths — a `WifiNetworkSuggestion` (API 31+; platform-managed city-scale auto-join/roaming whenever the primary Wi-Fi slot is free, spotted by a location-flagged Wi-Fi callback; the service declares the `location` FGS type for this) and a `WifiNetworkSpecifier` local-only secondary request for the dual-Wi-Fi case, filed ONLY when a scan shows `!FIPS` in range (a periodic scan kick runs while armed and unjoined; the system barely scans on its own) with the strongest beacon's BSSID pinned (SSID-only requests re-prompt even for approved APs — observed on Android 17; approval is stored per BSSID, so pinned = silent rejoin, and a specifier session is one-shot: on loss it is torn down and re-filed on the next sighting). Neither join is an underlay candidate (`preferredUnderlying` excludes the hotspot network); on join the service rebinds the node with `hotspot: {addr, prefix_len}`, which the shim turns into a second UDP transport bound to that address on the main instance's port (both instances carry `share_port`, or the second bind fails with EADDRINUSE and the node starts DEGRADED on one transport — this shipped broken from 0.4.0 until the `share_port` pin, because upstream moved the reuse flags after bind and the only test checked the config's shape, not that two sockets actually bound; `engine::tests::hotspot_overlay_starts_both_transports` now does. Unicast delivery prefers the most-specific socket, so the single mDNS-advertised port serves every interface) with `dial_prefixes` = the link subnet, and `protectFd` moves the matching socket onto the hotspot `Network` via `bindSocket` (wildcard/protected sockets otherwise route via the default network only).

UI conventions (the 2026-09 refresh): one theme, `Theme.Fips`, maps the **full** Material 3 role set onto `fips_*` colours, and every one of those has a `values-night/colors.xml` twin (navy surfaces from the launcher icon) — a colour added to one file needs the other, and a `colorPrimary`-only theme is what made dark mode unreadable before. Layouts use the shared `Widget.Fips.*` styles (`Card`, `Summary`, `Label`, `Mono`, …) instead of per-view radius/colour attributes. The project builds with `android.nonTransitiveRClass=true`, so Kotlin cannot resolve Material's `R.attr.*`: state-dependent colours are XML state lists (`res/color/power_bg.xml`: activated = connected, selected = starting) and Kotlin only flips view states. Overview's connection card is a **single toggle**, not a Connect/Disconnect pair, and its meaning is derived from three signals — `FipsNative.status().running`, `FipsVpnService.tunnelActive` (true from `ACTION_CONNECT` to `shutdown()`, so it stays true across a rebind while the engine reports not-running for ~2 s) and `MainActivity.isConnecting()` (a 3 s bridge from the tap to the service picking the intent up). Only when all three are false does a tap mean "connect"; do not key anything off `isRunning()` alone (the identity guard and Settings' "reconnect to apply" check `tunnelActive` too). The UI is not the guard, though — the service is: `ACTION_CONNECT` is ignored while `tunnelActive` (a second one used to establish a second tunnel, get "already running" from the shim, and take the error path into `shutdown()`), `connect()` re-checks after `establish()` and after `FipsNative.start()` that it has not been cancelled (`stillWanted`, a counter `shutdown()` bumps — Overview offers "tap to cancel" while connecting), and `rebindOnce` does nothing once `tunnelActive` is false, so a rebind queued before a Disconnect cannot bring the VPN back. Shutdown and connect are serialised: stopping the engine takes seconds on a phone (~5 s on a Pixel 9 Pro), so `shutdown()` takes ownership of its session's tun fd up front (it used to read `tunFd` at the END of its thread and closed a newer tunnel's fd, leaking the old one as an inert `tun0`), and an `ACTION_CONNECT` that arrives while `stopping` is queued and served by `finishShutdown()` on the same service instance — it used to run alongside the tail of the shutdown and be taken down by its `stopSelf()`. A Disconnect cancels a queued connect. `establishTunnel` counts the apps it actually allowed and falls back to capturing only fips2go when that is zero: a builder with no allowed application is a whole-device VPN, reachable before by uninstalling the only selected app. Settings' Save button is an extended FAB shown exactly while `hasUnsavedChanges()` holds (re-derived on every widget change, never a dirty flag) — a new persisted widget must be added to `SWITCHES`/`TEXT_FIELDS` as well as to `load`/`save`/`hasUnsavedChanges`. Snackbars and non-secret clipboard copies go through `Ui.snack`/`Ui.copy` (anchored above the bottom navigation; no duplicate "copied" toast on Android 13+); the nsec still goes through `OverviewFragment.copySecret` only.

Zero-config first run (0.3): a fresh install connects without the user opening Settings. `ConfigStore.applyDefaults()` — called from both `MainActivity.onCreate` and `FipsVpnService.onStartCommand`, since always-on VPN starts the service with no UI — seeds a bootstrap peer (`test-de01`) plus the toggle defaults, and deletes `RETIRED_KEYS`. It seeds only keys the user has never saved (`contains()`), which is what makes it safe on an upgrade: `SettingsFragment.save()` writes every key, so an existing choice — including a deliberately blanked field — is never overwritten. Nostr rendezvous and the in-app `.fips` resolver are now hardcoded on in `buildConfigJson`. Nostr is **not** peer discovery by default: the app leaves `node.rendezvous.nostr.policy` at fips's `configured_only`, so no unconfigured peer is dialed from an advert. Settings → "Discover peers via Nostr" (`nostr_discovery`, `DEF_NOSTR_DISCOVERY` = false) flips it to `policy: open` through the shim, which also sets both bounds to `nostr_discovery_max_peers` (default 3): `open_discovery_max_pending` (fips's own knob, the queue) and `open_discovery_max_peers` (fork knob @ ae22165/f4a811e, a ceiling on the overlay pool as a whole — queued + connecting + connected; sent from `DEF_NOSTR_DISCOVERY_MAX_PEERS`, which is also what the Settings summary quotes, so the number on screen and the bound in the node are one constant). The second exists because a queued peer leaves the queue when it connects, so `max_pending` alone bounds the growth *rate* and the only size bound was `max_peers` = 128; lowering `max_peers` instead would also cap LAN and inbound peers. It is a ceiling, not a set-point — nothing dials to reach it — and `0` in the shim means the default, not unlimited. What Nostr does on the phone: advertise the node, keep the relay connections the Overview card shows, and — since the shim sets `via_nostr` on every configured peer whenever Nostr is on (fips rejects it otherwise) — append a configured peer's advertised endpoints as fallback after its static address, so a bootstrap that moves is re-found. Links therefore come only from configured peers and mDNS: the one bootstrap the user picked plus, with `bootstrap_fallbacks` on (default), the first `FALLBACK_COUNT` of `FALLBACK_BOOTSTRAPS` whose npub differs from it (`ConfigStore.fallbackPeers`), so a single server outage does not empty the mesh; STUN, transports and DNS upstreams are omitted entirely so fips uses its built-in defaults. Relays are omitted too **unless the user customised them** (`RelaysActivity`, opened from Overview's "Nostr relays" card): the list lives under the pref key `relay_list` — NOT `nostr_relays`, which is the pre-0.3 setting's name and sits in `RETIRED_KEYS`, so `applyDefaults` would delete it on every launch. An absent key means "never customised": nothing is sent and fips's built-in relays apply (and keep applying across pin bumps); `ConfigStore.DEFAULT_RELAYS` is only a display mirror of that fips default — check it against fips `src/config/node.rs` when bumping the pin. Every relay passes `ConfigStore.normalizeRelay` both when stored and again in `buildConfigJson`, because fips adds each one with `add_relay(..)?` — a single URL nostr-sdk rejects fails the node's whole Nostr bootstrap. The last relay cannot be removed (the shim reads an empty list as "defaults", so an empty editor would lie), the list is capped at `MAX_RELAYS`, and a change made while connected is applied like a mesh-app change: one `requestRebind()` on leaving the screen, since fips fixes its relay pool at node start. Settings keeps only everyday toggles at the top level, with peer npub/endpoint/transport, inbound ports, split tunnel, worker threads and log level behind a collapsed Advanced group. FIPS Hotspot defaults on, so `MainActivity` shows a one-time rationale before the fine-location prompt on the first connect (Settings' own prompt is now the follow-up path, not the only one) — it runs *before* the notification/battery-exemption prompts, which would otherwise stack a system dialog and a settings Activity over it.


## Constraints & gotchas

- `shim/.cargo/config.toml` forces 16 KB page alignment (`max-page-size=16384`) on `aarch64` and `x86_64` — required on Android 15+/Pixel 9-class devices; don't remove it. `armeabi-v7a` stays 4 KB (32-bit Android never uses 16 KB pages).
- Three ABIs are built; the **debug** APK packages all of them (`arm64-v8a`, `armeabi-v7a`, `x86_64`) while **release builds ship one APK per ABI plus a universal APK** carrying all three (`-PreleaseAbi` drives the release `abiFilters` and takes a comma-separated list — one ABI per per-ABI APK, the full list for the universal one; only `arm64-v8a` is device-verified). The universal APK is a first-install convenience for the release page only; the per-ABI APKs are what the updater consumes, and a partial `./release-build.sh <abi>` run skips the universal build rather than package stale `jniLibs/` output. The ABI list lives in three places that must stay in sync: `build-native.sh`, `rust-toolchain.toml`, and the debug `abiFilters` in `android/app/build.gradle.kts`. 32-bit `armeabi-v7a` is the build most likely to break on a fips pin bump (pointer-width casts — e.g. bionic's 32-bit `msghdr.msg_namelen` is `i32`); build it before bumping the pin.
- Releases: **`RELEASING.md` is the full step-by-step** (version decision, build, GitHub release, Zapstore publish, credential handling) — follow it rather than reconstructing the sequence. `./release-build.sh` (signs via gitignored `android/keystore.properties` → keystore at `~/.android-keys/fips-android-release.keystore`; unsigned fallback when absent). It archives an unstripped `.so` per release for symbolication and verifies ABI contents, 16 KB alignment, and the signature. Bump `versionCode` + `versionName` together. Versioning policy (adopted after 0.1.6; earlier releases bumped the patch digit for everything): pre-1.0 semver — **minor** (0.2 → 0.3) for new user-visible features, **patch** (0.2.0 → 0.2.1) for bug fixes/polish; **1.0** is reserved for the native npub-addressed API milestone (replacing the interim IPv6/TUN compat layer). `versionCode` stays a plain monotonic counter (+1 per release) independent of the name; the in-app updater compares dotted numerics, so differing segment counts (`0.2` vs `0.1.6`) are fine. `THIRD-PARTY-NOTICES.md` is generated from the arm64 `cargo tree` (no GPL links into the Android build — `rustables` is host-only) and must be regenerated on a fips pin bump. Installing a release over the debug build (or vice versa) requires an uninstall — different signing keys — which wipes app data **including the mesh identity**, since the nsec is sealed by a non-exportable Keystore key that dies with the uninstall and `allowBackup="false"` rules out `adb backup`. Since 0.3 this is survivable *if you plan ahead*: Overview → **Back up** reveals the nsec to copy, and **Restore** takes it back afterwards. There is still no way to recover an identity from a build that has already been uninstalled, and a device running a pre-0.3 build cannot back up at all — check what is installed (`adb shell dumpsys package org.fips.android`) and compare signers (`apksigner verify --print-certs`) before an uninstall.
- min SDK 26, target/compile SDK 34.
- **Always-on VPN is opted out of** (`android.net.VpnService.SUPPORTS_ALWAYS_ON = false` on the service, honoured from API 27). Android starts an always-on service with the bare `android.net.VpnService` action, which `onStartCommand` does not treat as a connect, so the service sat bound with no tunnel — and with "Block connections without VPN" on, the selected apps had no connectivity until the user opened the app and tapped connect (seen on a Pixel 9 Pro running 0.4.1). `applyDefaults()` is still called from `onStartCommand` because API 26 ignores the opt-out and can start the service with no UI. Supporting always-on for real means handling that start as a connect *and* the no-UI failure modes (no VPN consent yet, identity error) — do not just delete the meta-data.
- **Release asset names are load-bearing.** `Updater.kt` picks a GitHub release asset by suffix — `-<abi>.apk` and `-<abi>.apk.sha256` — which is exactly what `release-build.sh` emits into `dist/v<versionName>/`. Renaming or omitting either artifact silently breaks in-app updates for already-installed users (the check returns "no update"), and no later release repairs it, because the same mismatch recurs. This is why the universal APK is an *addition* rather than a replacement, and why its `-universal` suffix must keep matching no ABI — `release-build.sh` asserts that — or every client would pull 40 MB instead of its own ~18 MB APK. The updater downloads, verifies the sha256, and hands the APK to the system installer, which enforces the release signing key and refuses while the VPN is connected.
- Don't reinstall or force-kill the app while the VPN is connected — it can leak netd routing rules that block other apps' connectivity until reboot. Disconnect first.
- Launcher icon assets (`android/.../res/mipmap-*`) are generated from the fips repo's `docs/logos/fips_logo.png` (mesh graphic cropped, luminance→alpha, adaptive icon + monochrome layer).
- `PHASE1-NOTES.md` / `PHASE2-NOTES.md` / `PHASE3-NOTES.md` document the porting history, the full socket-protect coverage table, and verification status — consult them before changing the embedding seam. Much of this codebase's behaviour is the result of a specific device-observed bug, and the commit message usually explains it: search history for a file before changing it.
